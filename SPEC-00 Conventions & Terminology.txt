SPEC-00: Conventions & Terminology

Version: 0.1 (Draft)
Status: Draft — open for RFC review
Supersedes: none
Dependencies: none
Applies to: every other SPEC-NN document, every conforming implementation of loc, lopm, lolsp, lofmt, lodoc, lotest, runtime, and every language pack under langpacks/
1. Motivation

A specification that is used by more than one implementation, in more than one natural language, by more than one team, in more than one country, must first agree on how it is read. This document defines:

    The keywords that carry normative weight (MUST, SHOULD, MAY).

    The identifiers used to tag rules so conformance tests can reference them.

    The versioning schemes used for the language, for language packs, for the LIR, and for this specification set.

    The definition of a conforming implementation, so that the Lingua Omnibus Foundation can certify independent compilers.

    The terminology — a normative glossary whose terms are the only legal ones used in the rest of the specification set — translated into every initial language pack.

Every rule in this document is testable. Any statement that cannot be expressed as a test is intentionally excluded and moved to non-normative notes at the end of each section.

This document is the contract that makes Principle 2 (spec-driven, not implementation-driven) enforceable.
2. Normative specification
2.1 Requirement keywords

CONV-001. The keywords MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, NOT RECOMMENDED, MAY, and OPTIONAL in this specification set MUST be interpreted as described in BCP 14 (RFC 2119 + RFC 8174) when, and only when, they appear in all capitals.

CONV-002. Implementations MUST treat all-lowercase uses of these words (e.g. "must", "should") as ordinary English prose, carrying no normative weight.

CONV-003. Documentation produced by an implementation (error messages, lolsp diagnostics, lodoc output) SHOULD preserve the all-caps convention when quoting a normative rule by its ID.
2.2 Rule identifiers

CONV-010. Every normative requirement MUST carry a stable identifier of the form:
{PREFIX}-{NNN}

where PREFIX is an uppercase ASCII token identifying the document (see table 2.3), and NNN is a zero-padded three-digit integer, assigned sequentially, never reused, never reordered.

CONV-011. Rule identifiers MUST NOT be renumbered after the specification document reaches Status: Stable. Corrections MUST use a new identifier and deprecate the old one (see CONV-040).

CONV-012. Every rule identifier MUST be referenced by at least one conformance test. The test path is normative and MUST be:
conformance/{PREFIX-lowercase}/{NNN}/{slug}.lo

Example: CONV-001 → conformance/conv/001/keywords-allcaps.lo.

CONV-013. A conformance test MAY exercise multiple rule identifiers; the mapping from test file → covered rule identifiers is declared in a header comment inside the test file:
# covers: CONV-001, CONV-002

2.4 Versioning

CONV-030. The Lingua Omnibus language version MUST follow Semantic Versioning 2.0.0 (MAJOR.MINOR.PATCH). A MAJOR bump indicates a breaking change to the grammar, type system, memory model, effects, or LIR format. A MINOR bump adds features without breaking existing conforming programs. A PATCH bump corrects documentation or bug-fix-only clarifications.

CONV-031. The LIR format MUST have its own version, independent of the language version, also SemVer 2.0.0, communicated in the LIR file header (see SPEC-06). This permits a language version 1.4.0 to emit LIR 1.2.0.

CONV-032. Language packs MUST be versioned by an ISO 8601 date of the form YYYY-MM-DD, not by SemVer, because natural-language keyword changes are not semantically comparable. The current pack version MUST be recorded in every language pack's keywords.json under the field "version".

CONV-033. This specification set (SPEC-00 … SPEC-13) MUST be versioned as a whole with a two-part version spec-{MAJOR}.{MINOR}, where MAJOR increments only when a rule identifier is removed or its meaning is broken, and MINOR increments on any additive or clarifying change. The current version is spec-0.1.

CONV-034. A conforming implementation MUST declare, in a machine-readable form, which spec-{MAJOR}.{MINOR} it implements, which language pack versions it bundles, and which LIR version it emits. The declaration format is:
{
  "implementation": "loc",
  "implementation_version": "1.4.0",
  "spec_compatibility": "0.1",
  "bundled_langpacks": { "en": "2026-01-01", "ro": "2026-01-01" },
  "lir_version": "1.2.0",
  "conformance": {
    "conv": "pass",
    "lex":  "pass",
    "gram": "pass",
    "type": "pass"
  }
}

The file MUST be retrievable via loc --version --json and MUST be preserved by lopm publish.
2.5 Conforming implementation

CONV-040. An implementation is a conforming implementation of spec-{MAJOR}.{MINOR} if and only if it:

    MUST pass 100% of conformance tests for every rule identifier whose prefix it declares as "pass" in its compatibility declaration (CONV-034).

    MUST declare every prefix as pass, partial, or unsupported. There is no default.

    MUST NOT declare pass for a prefix if any test in conformance/{prefix}/ fails.

    SHOULD pass 100% of CONV, LEX, GRAM, TYPE, LIR at minimum to be considered a useful implementation.

    MAY omit prefixes entirely (e.g. a compiler without quantum support declares quantum: unsupported), but MUST NOT silently accept syntax it cannot honour.

CONV-041. A conforming implementation MUST NOT add behaviour that contradicts a MUST in any pass prefix. It MAY add extensions outside the specification, provided that:

    Extensions are opt-in via an explicit flag or pragma (e.g. #pragma extension vendor_x).

    Extensions are documented in the implementation's own changelog with the prefix X-{vendor}.

    Extensions MUST NOT change the meaning of a program that compiles without them.

CONV-042. Programs that do not require an extension MUST compile identically on any two conforming implementations declaring the same spec_compatibility and the same lir_version. "Identically" here means: the generated LIR after optimization passes documented as optional in SPEC-06 MUST be byte-identical.
2.6 Deprecation

CONV-050. A rule identifier is deprecated when a new rule supersedes it. Deprecation MUST be recorded in the "Change log" of the owning document with a table row: | deprecated | {OLD_ID} | superseded by {NEW_ID} |.

CONV-051. A deprecated rule identifier MUST remain normative for at least one spec-MAJOR cycle. During deprecation, implementations MUST emit a warning (not an error) when triggering the deprecated behaviour, unless the program opts out via #pragma allow deprecated {OLD_ID}.

CONV-052. A deprecated rule identifier MUST be removed only in a spec-MAJOR bump, and the removal MUST be documented in a MIGRATION-{MAJOR}.md file at the repository root, following the LTS promise in Principle 13.
2.7 Language pack contract

CONV-060. A language pack is the only mechanism by which a natural language becomes usable in Lingua Omnibus. Language packs MUST be pure data — a directory containing at minimum:

    keywords.json (schema: spec/appendix/langpack-schema.json)

    types.json

    grammar-notes.md (non-normative prose describing SOV/SVO, RTL, CJK, etc.)

    tests/ (at least one test per keyword)

    version field inside keywords.json, matching CONV-032

CONV-061. Adding a new language pack MUST NOT require changes to loc or any other tool. If a language cannot be expressed by the current pack schema, the correct response is a new RFC proposing an extension to appendix/langpack-schema.json, not a compiler patch. This rule is the operational meaning of Principle 13.

CONV-062. A language pack MUST NOT introduce a keyword that aliases a keyword from another pack in a way that makes auto-detection ambiguous, unless the pack explicitly declares "requires_explicit_lingua_directive": true in its keywords.json.

CONV-063. Every language pack MUST include at least the following 40 keyword slots (values are pack-specific; the slots are universal):

KW_FUNCTION, KW_RETURN, KW_VAR, KW_CONST, KW_IF, KW_ELSE, KW_WHILE, KW_FOR, KW_IN, KW_BREAK, KW_CONTINUE, KW_MATCH, KW_STRUCT, KW_ENUM, KW_INTERFACE, KW_IMPL, KW_IMPORT, KW_EXPORT, KW_TRUE, KW_FALSE, KW_NULL, KW_AND, KW_OR, KW_NOT, KW_QUANTUM, KW_QUBIT, KW_MEASURE, KW_EFFECT, KW_WITH, KW_TRY, KW_CATCH, KW_RESULT, KW_OPTION, KW_ASYNC, KW_AWAIT, KW_SPAWN, KW_DB, KW_SELECT, KW_INSERT, KW_UPDATE.

CONV-064. A language pack MAY add additional keyword slots, but their identifiers MUST match the pattern KW_X_{NAME} and MUST be declared in grammar-notes.md with a link to the RFC that introduced them.
2.8 Unicode baseline

CONV-070. All source files, LIR text files, language pack files, and tool output MUST be UTF-8 encoded (RFC 3629), without a BOM.

CONV-071. All text MUST be normalized to Unicode NFC before tokenization. Source files that are not NFC MUST be accepted; the normalization is performed by the frontend, not required of the author.

CONV-072. Implementations MUST support the full Unicode 15.0+ code point range for identifiers and strings, subject to the rules in SPEC-01 §Identifiers.

CONV-073. Implementations MUST accept both \n (LF) and \r\n (CRLF) as line terminators and MUST normalize to LF in LIR output and in lofmt output unless the target file was CRLF and the user passed --preserve-eol.

3.4 Reserved words in the specification

CONV-076. The following lowercase words are reserved in this specification set for technical meaning and MUST be italicised on first use in every SPEC-XX: language pack, keyword slot, conformance test, rule identifier, unified AST, conforming implementation.
4. Examples
4.1 Example — the same program in EN and RO, byte-identical LIR

English (examples/hello/hello-en.lo):

#lingua: EN
function main() returns Unit:
    print("Hello, world!")
	
Romanian (examples/hello/hello-ro.lo):
lir 1.2.0
module hello {
  fn main : () -> unit {
  entry:
    %msg = const.str "Hello, world!"
    call @std.io.print(%msg)
    ret unit
  }
}
Conformance: Both files MUST produce byte-identical LIR. The test is conformance/conv/030/hello-bilingual.lo (which reads both source files and asserts diff is empty).

This example is the operational definition of Principle 2 (spec-driven): the compiler has no English-specific or Romanian-specific branch in the LIR generator; the difference is entirely inside the two language packs.
4.2 Example — version declaration

{
  "implementation": "loc",
  "implementation_version": "0.9.0",
  "spec_compatibility": "0.1",
  "bundled_langpacks": { "en": "2026-01-01", "ro": "2026-01-01", "fr": "2026-01-01" },
  "lir_version": "0.3.0",
  "conformance": {
    "conv": "pass",
    "lex": "pass",
    "gram": "pass",
    "type": "pass",
    "mem": "partial",
    "eff": "unsupported",
    "lir": "pass"
  }
}

loc --version --json on this build MUST output exactly this document, sorted by key for byte-identical output across runs.

4.3 Example — conformance test header:

# conformance/conv/001/keywords-allcaps.lo
# covers: CONV-001, CONV-002
#lingua: EN

# MUST parse: the all-caps keyword IF is normative.
# MUST fail: the lowercase "if" is prose, not a keyword.

function main() returns Unit:
    IF true THEN:
        pass
		

The test harness asserts that loc check returns exit code 0 for the all-caps form and exit code 1 for the lowercase form. The lowercase form is exercised in a sibling file keywords-lowercase-fails.lo.

6. Interactions with other sections

    SPEC-01 (LEX): consumes CONV-070 … CONV-073 for encoding and normalization; consumes CONV-060 … CONV-064 for keyword mapping.

    SPEC-02 (GRAM): each grammar rule MUST be tagged with a GRAM-NNN identifier; the mapping to the language-pack keyword slot is declared in grammar-notes.md.

    SPEC-06 (LIR): MUST honour CONV-031 (independent version) and CONV-034 (declared LIR version). LIR byte-identical output is required by CONV-042.

    SPEC-09 (TOOL): loc, lopm, lolsp, lofmt, lodoc, lotest MUST expose the compatibility declaration of CONV-034 in their machine-readable version output.

    SPEC-12 (COMPAT): extends CONV-030 … CONV-034 with the migration-tool rules for spec-MAJOR bumps.

    SPEC-13 (GOVERNANCE): governs how new CONV-NNN identifiers are proposed and approved.

7. Open questions

Q1. Bootstrap chain and spec-0.1. Principle 4 requires bootstrappability, but spec-0.1 does not yet define the maximum length of the chain. Proposal: RFC-0002 to define "TCC → LO-0 → LO-1" as a maximum of three stages, with a formal proof obligation in docs/bootstrapping.md. Deferred to SPEC-12.

Q2. Vendor extension lifecycle. CONV-041 allows extensions but does not define how they sunset. Proposal: any extension older than two spec-MINOR cycles without an accepted RFC MUST be dropped from the reference implementation. Deferred to SPEC-13.

Q3. Federated registry discovery. CONV-080 (see below) declares federation but does not define the discovery mechanism. Proposal: a registry.toml file in every package root, plus DNS _lopm._tcp lookup as an optional hint. Deferred to SPEC-09.

Q4. Language pack deprecation. CONV-032 dates packs but does not deprecate old dates. Proposal: a pack more than 24 months old on a spec-STABLE release is deprecated; implementations MAY still accept it with a warning. Deferred to SPEC-12.

Q5. Spec text translation. This specification is normative in English only. Translations exist in docs/spec-translations/ but are informative. Should the foundation eventually certify normative translations, and if so, in which languages first? Open for community vote after spec-1.0.

9. Appendix A — CONV-080: Federated registry

CONV-080. The lopm package manager MUST support at least two modes of operation:

    Local mode — a vendor/ directory or a file:// path acting as a registry. This mode MUST be enabled with zero configuration; lopm install --vendor MUST work with no network.

    Remote mode — any HTTP(S) endpoint serving the standard registry layout (defined in SPEC-09). There is no mandatory "official" registry. The Lingua Omnibus Foundation MAY operate a reference registry for convenience, but it MUST NOT be the only registry, and it MUST NOT be required for lopm to function.

A conforming implementation of lopm MUST allow the user to configure arbitrary registries via lopm.toml:

[registries]
default = "https://my-company.example/lopm"
mirror  = "file:///srv/lopm-mirror"

[registries.policy]
fallback = ["default", "mirror"]
offline  = false

This rule operationalizes Principles 1 (zero vendor lock-in) and 5 (federated packages).
